# Sessão 2025-05-12 — Investigação e Correções do Funil

## Problema Central

O chefe reportou **88 contratos em abril** (50 Emissão + 38 Registro).  
O dashboard filtrado para abril mostrava **41** (30 + 11). Investigamos o porquê.

---

## Causa Raiz — Tripla

### 1. Bug no filtro de data (`api.py` — `/dashboard`)

**Antes (bug):**
```python
df = df[dt.dt.date >= inicio]   # filtra linhas por DT_INICIO_FASE
df = df[dt.dt.date <= fim]
# _build_dashboard_data aplica check de Simulação DEPOIS
# → ops que iniciaram em janeiro e chegaram à Emissão em abril eram excluídas
#   (sem linha de Simulação em abril → check descartava a op inteira)
```

**Depois (correto):**
```python
# Compute Simulação set from FULL dataset BEFORE date filter
ops_com_sim = set(df.loc[df['NU_FASE_OPERACAO'].isin({0, 1}), 'NU_OPERACAO']...)
# Row-level date filter
df = df[dt.dt.date >= inicio]
df = df[dt.dt.date <= fim]
# Apply integrity filter using full-dataset set
df = df[df['NU_OPERACAO']...isin(ops_com_sim)]
```

### 2. Mapeamento de macrofases — fases 500–505 e 600–701

Em um commit anterior foi alterado:

| | Antigo (correto) | Novo (quebrou) |
|---|---|---|
| Emissão de Contrato | fases 500–505 | só 500–501 |
| Registro de Contratos | fases 600–701 | removido / virou "Formalização" |
| `_MACROFASE_MIN_CODE` | Emissão=500, Registro=600 | Emissão=501, sem Registro |

**Revertido para o antigo.**

### 3. Lógica de `count` no MacroMilestones

Em um commit anterior a lógica foi trocada para:
```javascript
// ERRADO — soma phase_counts (duplica ops que passaram por múltiplas fases)
const count = mf.id === 'Emissão de Contrato'
  ? phases.reduce((s, p) => s + p.total, 0)   // dava 204, não 50
  : macroTotalMap.get(mf.id) + reprovados;
```

**Revertido para:**
```javascript
// CORRETO — usa op_max_pipeline (contagem única)
const count = (macroTotalMap.get(mf.id) ?? phases.reduce((s, p) => s + p.total, 0)) + reprovados;
```

### 4. Override incorreto no MacroPhaseBar (introduzido hoje)

No início desta sessão adicionamos um override que fazia MacroPhaseBar usar `phase_counts` para Emissão. Isso era errado pelos mesmos motivos do item 3. **Revertido.**

---

## Por que 30 vs 50 — explicação final

| Métrica | Definição | Valor |
|---|---|---|
| `phase_counts[501]` | ops com linha *exatamente* na fase 501 em abril | 30 |
| `op_max_pipeline >= 500` | ops únicas que *chegaram a qualquer fase ≥ 500* em abril | ~50 |

Os 20 a mais são ops que entraram na fase 501 em abril e **dentro do mesmo mês** já avançaram para fase 502–505. Elas têm op_max_pipeline ≥ 500, mas não têm mais linha em fase 501 no recorte de abril. O relatório do chefe conta essas também → usa lógica cumulativa (op_max_pipeline).

---

## Gap residual entre nosso 50 e o 50 do chefe

Mesmo com a correção, pode sobrar uma diferença de ±5 ops. Motivo:

- Ops que entraram na Emissão em março e **ficaram paradas** (sem nenhum novo registro em abril) aparecem no banco vivo mas não têm linha de DT_INICIO_FASE em abril → excluídas pelo nosso filtro.
- Para fechar 100%: precisaria de snapshot do banco vivo (estado atual de cada op) ou uma coluna `DT_ULTIMO_REGISTRO` por operação no ETL.

## Contexto do Problema — Glossário

| Termo | Definição |
|---|---|
| `op_max_pipeline` | Máximo de NU_FASE_OPERACAO por operação, excluindo canceladas — usado para contar "chegou até aqui" |
| `phase_counts` | Operações únicas *com registro nessa fase específica* — menor, conta só quem passou por exatamente essa fase |
| `macrofaseTotais` | Array do backend: `[{ macrofase, total }]` onde total = `op_max_pipeline >= threshold` |
| `operacoesPorFase` | Array do backend: phase_counts por fase específica |
| `DT_INICIO_FASE` | Data em que a op *entrou* naquela fase — não é data de conclusão |
